# Design: TripSplitter, a Telegram bot and Mini App for splitting trip expenses

Generated by /office-hours on 2026-09-27
Branch: unknown (not yet a git repository)
Repo: tripspliter (local, empty folder)
Status: APPROVED
Mode: Builder

## Problem Statement

Splitting costs on a group trip means leaving the group chat, opening a separate app that everyone has to install, and typing in receipts by hand. Free tiers of existing tools cap usage or charge for receipt reading. The goal is a bot that lives in the Telegram group the trip already uses, reads receipt photos with an LLM, and records who owes whom.

This is a side project for the builder's own trips. It is not a business.

## What Makes This Cool

Someone posts a photo of the dinner receipt in the group. The bot replies within seconds with the merchant, total, currency and line items, and the person who paid splits it in a couple of taps. Nobody installs anything or signs up.

## Constraints

- Keep it simple. User's words: "keep it simple for now".
- Adding an expense must not need the whole group. User's words: "should not require the intire group to interact on every add". The person adding the expense completes it alone.
- No paid third-party product. The builder pays LLM API fees directly.
- Telegram Bot API limits:
  - Bots cannot list group members. The roster is built from message senders, join and leave events, and the admin list.
  - Bots cannot read messages sent before they joined.
  - Mini App buttons of type `web_app` work only in private chats. Groups use a direct link of the form `t.me/<bot>/<app>?startapp=<token>`.
  - The Mini App does not receive the group chat ID, so the token must identify the group and be signed.
- These limits come from prior knowledge of the Bot API and were not checked against the live documentation in this session. Verify during the first build step.

## Premises

1. Similar bots exist. SplitFast has AI receipt scanning but its free tier allows 10 expenses in total, 4 per day and 5 visible members, so it is paid in practice (source: a summary of splitfast.io fetched on 2026-09-27, not tested first-hand). TabMate showed 5 commits on the same date (github.com/alexandrmotologa/tabmate). Building our own is justified in any case because this is a personal project.
2. The person adding an expense does all the work. Others tapping to claim their own items is an optional later extra.
3. Exactly three split types: evenly, by portions, by item.
4. The bot runs with privacy mode off so it receives all group messages, and uses them only to learn who is in the group. It stores no message text. It reads a photo only when the photo is tagged with the bot's name, and only tagged photos are sent to the external LLM. The intro message says this plainly.
5. The bot records debts only. It never moves money.

## Approaches Considered

### Approach A: Bot plus Mini App (chosen)
The bot handles the group: roster, receipt photos, summaries. The Mini App handles adding and editing expenses, assigning items, and balances. Effort: medium. Risk: low. Needs HTTPS hosting.

### Approach B: Chat-only bot
Rejected: by-item splitting through chat buttons is awkward on long receipts.

### Approach C: Fork TabMate and add receipt reading
Rejected: the repository is 5 commits old and brings design choices the builder did not make.

## Recommended Approach

Approach A, built in stages so that something is usable after each stage.

### Components

- **Bot**: TypeScript with grammY. Long polling during development, webhook in production.
- **Mini App**: React and Vite, using the Telegram Web App SDK for theme and identity.
- **API**: a small HTTP server in the same process as the bot. Every request validates Telegram `initData` with the bot token, then checks that the user is in the stored roster for the trip or, if not, confirms group membership with `getChatMember` and adds them. Non-members are refused.
- **Link token**: the `startapp` value is an opaque trip ID signed with a server secret. It carries no chat ID and does not expire, because access is decided by the membership check and not by possession of the link.
- **Database**: SQLite for a first version, one file, no separate service. This commits the project to a small always-on server.
- **Access and cost control**: the bot only works in groups on an allowlist of chat IDs set by the owner. In any other group it posts one line saying so and does nothing else. Receipt reads are capped per group per day.
- **Group upgrade**: when a group becomes a supergroup Telegram issues a new chat ID. The bot handles the migration service message by updating the trip's chat ID. Links keep working because the token holds the trip ID.
- **Receipt reading**: an LLM vision call that returns structured JSON: merchant, date, currency, line items with quantity and price, tax, tip, total.

### Data model

- `trip`: one per group chat. Fields: chat ID, name, home currency.
- `member`: Telegram user ID, display name, trip, active flag. A placeholder member has a name and no user ID until claimed. Members with any history are never deleted. A member who leaves the group is marked inactive, is left out of default splits on new expenses, and keeps a visible balance that can still be settled. Senders flagged as bots and anonymous admin posts are never recorded as members.
- `expense`: trip, created-by member, payer, total in minor units, tax, tip, currency, FX rate to home currency, split type, description, receipt file ID, status (draft or confirmed).
- `expense_item`: expense, label, amount in minor units. Used for by-item splits.
- `share`: member, weight, and exactly one of expense or item. Even and portions splits reference the expense. By-item splits reference the item.
- `settlement`: created-by member, from member, to member, amount in home currency, date.

All amounts are integers in minor units. Per-member amounts are not stored. Balances are always recomputed from confirmed expenses and settlements, so an edit or delete takes effect everywhere at once. Drafts never count toward balances.

Rounding: remainders go to the payer if the payer is in the split. If not, they go to the included member with the lowest member ID. Shares always sum to the total.

Tax, tip, service charges and discounts on a by-item split are spread across members in proportion to their item subtotals. If the receipt's items already sum to the total, prices are treated as tax-inclusive and no tax is added. The adder can correct any extracted figure before confirming.

Balances and the settle-up list are in the trip's home currency, using the rate stored on each expense. The rate date is the receipt date, or the posting date if the receipt date cannot be read. If no rate can be fetched, the adder enters one. The adder can always override the rate.

Settle-up method: repeatedly match the member who is owed the most with the member who owes the most. This gives a short list of at most N-1 payments and the same result every time. It is not guaranteed to be the smallest possible list.

### Main flows

1. **Setup**: bot is added to a group, creates the trip, reads the admin list, posts an intro message with the Mini App link and a plain statement of what it reads and stores.
2. **Roster**: every message sender is added as a member. Join and leave service messages update the roster. The Mini App shows roughly how many members are known, using the group member count minus the bot itself, worded as approximate because other bots cannot always be told apart. People who have not posted are added by hand.
3. **Receipt**: the bot only looks at a photo when it is tagged, either by a caption that mentions the bot or by a reply to the photo that mentions the bot. Untagged photos are never downloaded, never sent to the LLM and never stored. For a tagged photo the bot always answers: either a draft (merchant, total, item count, assumed payer, which is the person who tagged it) with buttons "Split evenly" and "Open to split" that any member of the trip can use, or a message saying it could not read a receipt and offering manual entry. Whether a caption mention is delivered to the bot must be verified in step 3.
4. **Manual add**: from the Mini App, enter amount, payer, description and split type.
5. **Split**: evenly (choose who is included, default everyone), by portions (a number per person), by item (assign each line to one or more people, with tax and tip spread in proportion).
6. **Balances**: the Mini App shows net balance per member and the smallest set of payments that settles everything.
7. **Settle**: any member records a payment between two members as made, in the home currency. No confirmation from the other party is needed. Any member can undo it. The bot posts a one-line confirmation in the group and the action is written to the activity log.

### Failure handling

- Receipt reading fails or items do not sum to the total: the bot says so and offers the total only, with manual entry.
- Foreign currency: detected from the receipt, confirmed by the adder, converted at that day's rate, with the rate stored on the expense.
- Editing or deleting an expense: see Permissions and activity log below. The bot posts a one-line notice in the group, including the change in amount, so members can see why a balance changed.
- Duplicate receipt: if a new draft has the same merchant, total and date as an existing expense, the bot warns and lets the member continue.
- Receipts across several photos or an album: not supported in the first version. One photo per receipt, with manual correction.

### Permissions and activity log

Every member of a trip can do every action: finish or discard any draft, add, edit or delete any expense, add members by hand, record or undo any settlement, and end the trip. There are no roles. The builder's words: "everyone should have permissions to every action".

Because anyone can change anything, every change is recorded. The `activity` table holds: trip, acting member, time, action (create, edit, delete, confirm, discard, settle, undo settle, add member, claim member, end trip), the record affected, and the values before and after. Entries are never edited or removed. Deleting an expense marks it deleted and keeps the row, so the log can always show what it was. The Mini App has an Activity screen listing changes, newest first.

### Drafts

Drafts do not expire. They stay until a member finishes or discards them, and never count toward balances. The Mini App lists open drafts so they are not forgotten.

### Members added by hand

Any member can add a person by name in the Mini App. This is the override for anyone the bot has not seen. A person added by hand can be included in splits and settlements straight away. Later, a real Telegram user can claim that entry with one tap ("that's me"), which attaches their Telegram ID to the existing member so all history carries over. If the person was already picked up automatically as a separate member, claiming merges the two: shares, payments and settlements move to the surviving member, and the merge is written to the activity log. Claiming is optional.

### Ending a trip

An "end trip" action archives the trip as read-only. The next expense in the group starts a new trip with the same members. Home currency is chosen when a trip is created and can be changed later, which does not alter rates already stored on expenses.

## Open Questions

1. Which LLM and what it costs per receipt. Needs a pricing check before choosing.
2. Which provider to use for the small always-on server.
3. Defaults proposed in the walkthrough and not objected to, so treated as accepted unless the builder says otherwise: every known active member is in an even split by default, and each saved expense posts one line to the group.
4. Whether members are comfortable with privacy mode off. If not, the fallback is a photo captioned with a command. Under the fallback the bot no longer sees ordinary messages, so the roster is built only from people who use a command, tap a button or open the Mini App, plus placeholders.
5. FX rate source.
## Success Criteria

- On a real trip with the builder's friends, every shared expense is recorded through the bot and nobody opens another app.
- A receipt photo becomes a confirmed expense in under 30 seconds.
- A 12-line restaurant receipt is split by item by one person without help from the others.
- At the end of the trip the settle-up list matches a hand check.

## Distribution Plan

Users get it by adding the bot to a Telegram group. No install. The bot and Mini App are deployed as one web service. First version: manual deploy from the builder's machine. Automated deploy on push is deferred until the project is in a git repository with a remote.

### R2-1 — completeness

**Problem**

> The path for changing the assumed payer on a receipt draft is still not stated. Flow 3 sets the payer to the person who tagged the photo, and with reply-tagging that person is often not the one who paid. The document also does not say whether 'Split evenly' confirms the expense immediately in chat, which would leave no step at which the payer can be corrected before it counts toward balances.

**Remedy**

> State where the payer is changed (for example a payer picker on the draft in the Mini App, or a 'Change payer' button on the draft message) and whether 'Split evenly' confirms at once or opens a confirmation step.

### R2-2 — consistency

**Problem**

> Flow 6 still says the Mini App shows 'the smallest set of payments that settles everything', while the settle-up method paragraph says the greedy result 'is not guaranteed to be the smallest possible list'.

**Remedy**

> Reword flow 6 to 'a short list of payments that settles everything' to match the settle-up method.

### R2-3 — feasibility

**Problem**

> The supergroup migration behavior is now specified under Components, but it is not in the Constraints list that Next Step 3 verifies, so the chat ID change and the migration service message remain unverified assumptions with no step that checks them.

**Remedy**

> Add the group-to-supergroup chat ID change to the Telegram limits under Constraints, or name it explicitly in Next Step 3.

### R2-4 — completeness

**Problem**

> The API accepts any user found in the stored roster, and members who leave are kept as inactive rather than deleted. A person who left or was removed from the group therefore keeps full read and write access to the trip, including delete and end trip, because the token does not expire and the roster check passes before getChatMember is consulted.

**Remedy**

> Decide whether inactive members keep access. If not, refuse roster members whose active flag is off, or re-check getChatMember periodically, and state what a former member can still see.

### R2-5 — consistency

**Problem**

> The data model says 'trip: one per group chat', but Ending a trip creates further trips in the same chat. The trip has no status or archived field, the rule for picking the current trip of a chat is not stated, and the link in the intro message carries the old trip ID, so it would open the archived trip. How the members are carried over ('with the same members') is also undefined: member rows belong to a trip, and the document does not say whether inactive members and unclaimed hand-added members are copied.

**Remedy**

> Change the model to many trips per chat with a status field and at most one active trip, state how members are copied to the new trip, and state how the group gets the new trip's link (for example the bot posts a new link, or the token resolves to the chat's active trip).

### R2-6 — completeness

**Problem**

> Ending a trip makes it read-only, but trips normally end with unpaid balances. A read-only trip cannot record settlements, so debts from an ended trip can never be marked paid. Any member can end the trip and there is no reopen action, so an accidental tap is permanent.

**Remedy**

> State whether settlements remain allowed on an ended trip, and add a reopen action (logged in activity) or a confirmation step before ending.

### R2-7 — feasibility

**Problem**

> Home currency 'can be changed later, which does not alter rates already stored on expenses'. Stored rates convert to the old home currency, and settlements are held as amounts in the home currency. After a change, balances would mix values in two currencies and be wrong.

**Remedy**

> Either fix the home currency once the trip has a confirmed expense or settlement, or define the recalculation: re-fetch or re-enter rates for existing expenses and convert existing settlements, with the change logged.

### R2-8 — consistency

**Problem**

> The expense model has no date field and no merchant field. The duplicate warning compares merchant, total and date, and the FX rule uses the receipt date or posting date, so neither rule can be implemented with the stated schema. Manual expenses also have no date.

**Remedy**

> Add an expense date (and created-at time) and a merchant field to expense, or state that merchant is held in description and define the comparison accordingly.

### R2-9 — consistency

**Problem**

> Service charges and discounts are spread in proportion on a by-item split, but the receipt JSON returns only tax and tip and the expense model stores only tax and tip. The failure rule 'items do not sum to the total' also does not say what is included in the sum, so a receipt with a discount or service charge would be reported as a failed read.

**Remedy**

> Add service charge and discount to the extraction output and the expense model (or a single 'adjustments' figure), and define the check as items plus tax, tip and charges minus discounts equals total, with the tax-inclusive case as the stated exception.

### R2-10 — completeness

**Problem**

> Any member can delete any expense or discard any draft, and the rows are kept and logged, but there is no restore action. The log shows what was lost without a way to get it back, so a mistaken or hostile delete means re-entering the expense by hand.

**Remedy**

> Add a restore action from the Activity screen for deleted expenses and discarded drafts, or state explicitly that re-entry by hand is the accepted recovery in the first version.

### R2-11 — clarity

**Problem**

> Receipt reads are 'capped per group per day' with no number, and the behavior at the cap is not stated. Flow 3 says the bot always answers a tagged photo, so the reply when the cap is reached needs to be defined.

**Remedy**

> Give the cap value (or say it is a configuration setting with a default) and state that at the cap the bot replies that the daily limit is reached and offers manual entry.

### R2-12 — clarity

**Problem**

> Flow 1 says the bot creates the trip when added to a group, while Components say the bot does nothing in a group that is not on the allowlist. The order is not stated, and the owner needs the chat ID to allowlist a group but the document does not say how they get it.

**Remedy**

> State that the trip is created only for allowlisted groups, that the one-line refusal includes the chat ID, and how the owner adds an ID (configuration file, environment setting, or owner-only command).

### R2-13 — feasibility

**Problem**

> The settle-up method claims 'the same result every time', but no tie-break is given when two members owe or are owed the same amount. Without one the output depends on iteration order and the hand check in the success criteria may not match.

**Remedy**

> Add a tie-break, for example lowest member ID first, and cover it in the step 4 unit tests.

### R2-14 — completeness

**Problem**

> The merge on claiming does not cover collisions. If the hand-added member and the automatically added member both have shares on the same expense or item, or one is the payer and the other a participant, or a settlement exists between the two, moving records to the surviving member produces duplicate shares or a payment from a member to themselves.

**Remedy**

> Define the merge rules: add weights of duplicate shares on the same expense or item, and remove or void settlements between the two merged members, with both logged.
